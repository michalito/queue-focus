# Sync server operations

This is the server portion of the sync implementation. The desktop client
integration is still in progress; deploying this service alone does not enable
sync in the released apps. See [the design](sync-design.md) for behavior and
[progress](sync-progress.md) for the review checkpoints.

The server serves one person's shared queue. Each device has its own bearer
token and can read and change that queue. There are no public signup or admin
HTTP endpoints. Tokens are generated by the operator CLI, printed once and
stored as hashes. Queue contents are readable by the VPS operator.

## Local build and initial setup

Build with Rust 1.92 or newer:

```sh
cargo build --locked --release -p qf-sync-server
target/release/qf-sync-server init /path/to/private-sync-data/queue.db
target/release/qf-sync-server enroll /path/to/private-sync-data/queue.db Mac
target/release/qf-sync-server enroll /path/to/private-sync-data/queue.db Ubuntu
target/release/qf-sync-server serve /path/to/private-sync-data/queue.db
```

`init` creates the dedicated directory with mode 0700 and the database with
mode 0600. An existing directory must already be private. Creation never
overwrites an existing file. `serve` refuses missing or invalid databases;
it cannot silently replace a missing volume with a new empty shared queue.
The default listen address is `127.0.0.1:8787`.

Keep each enrollment token in that device's private credential file during
client setup. Do not put it in a URL, Compose file, source control or shared
logs. Enrollment output contains the secret; run it in a private terminal.
The enrollment UUID is safe to use for revocation and rotation:

```sh
qf-sync-server revoke /data/queue.db DEVICE_UUID
qf-sync-server rotate /data/queue.db DEVICE_UUID
```

Rotation retains the UUID so retries can still find that device's previous
receipts. Put the replacement token on the same device. Revocation affects
subsequent transactions; a transaction already committed remains committed.

## Dokploy on the VPS

Use the repository's `deploy/sync/compose.yaml`, with the repository root
available as its build context. The image runs as UID/GID 10001, has a read-only
root filesystem and uses two named volumes. Keep one service replica and route
a Dokploy HTTPS domain to the `qf-sync` service's internal port **8787**. Do not
publish that port on the VPS. HTTPS termination happens in Dokploy's proxy.

Build the image, then initialize and enroll before starting the service. From
the checkout on the server, these equivalent Compose commands are:

```sh
docker compose -f deploy/sync/compose.yaml build
docker compose -f deploy/sync/compose.yaml run --rm qf-sync init /data/queue.db
docker compose -f deploy/sync/compose.yaml run --rm qf-sync enroll /data/queue.db Mac
docker compose -f deploy/sync/compose.yaml run --rm qf-sync enroll /data/queue.db Ubuntu
docker compose -f deploy/sync/compose.yaml up -d
```

Use the same Compose project name and volume names for setup and the Dokploy
deployment. Dokploy may prefix them with its application name. Inspect those
names before setup; initializing a different project's volume leaves the
deployment's volume empty. Newly created Docker volumes inherit the image's
directory ownership. Existing volumes must be writable by UID 10001 and the
data directory must have mode 0700.

`GET /health` checks database availability and returns no queue data.
`POST /v1/exchange` requires `Authorization: Bearer TOKEN`,
`X-Queue-Focus-Device: DEVICE_UUID` and protocol version
1. It is the only data endpoint. Requests have a 4 MiB limit, at most eight
requests are admitted before reading bodies, and request processing has a
30-second deadline. A timeout does not mean a command failed: clients retain
and retry the same command ID.

## Consistent backups

Create an SQLite backup artifact while the service is running:

```sh
docker compose -f deploy/sync/compose.yaml exec qf-sync \
  qf-sync-server backup /data/queue.db /backups/queue-2026-10-20.db
```

Use a new filename for each backup. The CLI uses SQLite's online backup API,
syncs the completed file and publishes it atomically without replacing an
existing backup. Failed backup creation does not publish a partial artifact.
The artifact contains the queue, receipts, history, device token hashes and
server clock. Treat it as private.

Schedule the artifact command on the VPS before Dokploy's volume backup.
Configure Dokploy to copy **queue-backups**, not the live **queue-data** volume:
copying a live database together with independently copied WAL files is not
a consistent SQLite backup. Upload backups to private off-host storage and
set retention for both local artifacts and remote backups. Check backup
success and rehearse restoration before relying on it.

References: [SQLite backup API](https://www.sqlite.org/backup.html) and
[Dokploy volume backups](https://docs.dokploy.com/docs/core/volume-backups).

## Restore and recovery

1. Stop the service. Preserve the current data volume and all client data
   directories for recovery.
2. Copy a completed backup into a **new** private data directory/volume as
   `queue.db`, owned by UID 10001 with mode 0600. Do not mix it with an old
   database's `-wal` or `-shm` files.
3. With the service still stopped, run
   `qf-sync-server restore-generation /data/queue.db` against that copy.
4. Point the service at the restored volume and start it. Existing clients
   will report that recovery is required. Export and reconcile their pending
   work through the client recovery flow; do not delete their journals or
   bypass their history checks.

The generation change invalidates old concurrency tokens and undo eligibility.
Task identities and timer elapsed time are preserved. The server also retains
a hash for every revision, so a raw database rollback that later advances past
a client's revision is detected as divergent history. That check supplements
the documented restore procedure.

Backups also restore the token revocation state at the time they were taken.
Before exposing a restored service, revoke any devices removed since that
backup, or rotate their tokens as appropriate.
